# ✈️ AI-Powered Airline Assistant

A multilingual, Retrieval-Augmented Generation (RAG) chatbot for airline customer support. It answers passenger queries in **English, Hindi, Spanish, and French**, grounding every response in real airline policy and FAQ documents — and when it can't resolve a query, it escalates it by email to the right airline department with full conversation context.

Built with **React + FastAPI + SQLAlchemy (SQLite/MySQL) + ChromaDB + Google Gemini**.

---

## ✨ Features

- **Grounded, context-aware answers** — responses are generated by `gemini-3.6-flash` strictly from retrieved policy/FAQ chunks, dramatically reducing hallucination. The model replies as structured JSON (`{kind, answer}`), so classification never depends on parsing markers out of prose.
- **Multi-turn conversations** — each thread is a `conversations` row; recent turns are replayed to the model, so follow-ups like “and for business class?” resolve against the previous question.
- **Multilingual RAG** — `gemini-embedding-001` places all four languages in a shared semantic space, so a Hindi question can retrieve an English policy paragraph and get answered in Hindi.
- **Hierarchical, structure-aware chunking** — documents are split along their heading structure first (sections → paragraphs) with overlap, and every chunk carries metadata (`doc_title`, `section`, `language`).
- **Vector search with ChromaDB** — persistent local collection, cosine-similarity top-k retrieval with metadata filtering.
- **Secure authentication** — JWT-based sessions, bcrypt-hashed passwords.
- **Query logging** — every question, retrieved context, answer, language, and confidence score is logged to the database for analytics, and browsable in the UI’s **History** panel.
- **Department routing + human-in-the-loop escalation** — unresolved/low-confidence queries are classified into a department (Baggage, Refunds, Special Assistance, General) and emailed via SMTP to that team with the full conversation transcript and the policy excerpts that were retrieved. Passengers can also escalate any answer themselves with **“Not helpful — talk to a human”**.
- **Scope guard** — greetings/small talk get a friendly conversational reply steering to airline topics; off-topic questions (recipes, weather…) get a professional "airline queries only" redirect. Neither is escalated — only genuine airline questions the knowledge base can't answer reach a human.

## 🧰 Tech Stack

| ---------------- | ---------------------------------------------------------------- |
| LLM              | Google **Gemini 3.6 Flash** (`gemini-3.6-flash`) via `google-genai` SDK |

## 🚀 Getting Started

### 1. Prerequisites
- Python 3.10+, Node.js 18+ (MySQL 8 optional — SQLite works out of the box)
- A **Gemini API key** from [Google AI Studio](https://aistudio.google.com/)

### 2. Environment variables (`.env`)

Copy `.env.example` to `.env` and fill in your key:

```env
GEMINI_API_KEY=your_google_ai_studio_key

# Optional — defaults to backend/airline.db as an absolute path, so it resolves
# to the same file no matter which directory uvicorn was started from.
DATABASE_URL=

# Required in production. If left blank the backend generates a throwaway
# secret into backend/.dev_jwt_secret and logs a warning.
#   python -c "import secrets; print(secrets.token_urlsafe(48))"
JWT_SECRET=a_long_random_string

# Optional — leave blank to record escalations without sending email
SMTP_HOST=smtp.gmail.com
SMTP_PORT=587
SMTP_USER=your_email@gmail.com
SMTP_PASSWORD=your_app_password

# Optional — where each department's escalation email is sent. Blank uses the
# skywings.example placeholders in config.py, which go nowhere real.
BAGGAGE_EMAIL=
REFUNDS_EMAIL=
SPECIAL_ASSISTANCE_EMAIL=
SUPPORT_EMAIL=

# Optional tuning
CHAT_MODEL=gemini-3.6-flash
CORS_ORIGINS=http://localhost:5173,http://127.0.0.1:5173
MAX_MESSAGE_CHARS=2000
HISTORY_TURNS=6
```

### 3. Database

Tables (`users`, `conversations`, `query_logs`, `departments`, `escalations`) are **created and seeded automatically** on first backend start. For MySQL, create the database first (`CREATE DATABASE airline_assistant;`) and set `DATABASE_URL` accordingly.

### 4. Backend

```bash
cd backend
pip install -r requirements.txt
python rag/ingest.py          # index docs/ into ChromaDB (needs GEMINI_API_KEY)
uvicorn main:app --reload     # http://localhost:8000
```

Check `GET /health` — `indexed_chunks` must be non-zero, otherwise retrieval
finds nothing and every question escalates.

Run the tests (no Gemini key required — the model is mocked):

```bash
pip install -r requirements-dev.txt
python -m pytest tests -q
```

For a live end-to-end check against the real Gemini API and real SMTP — RAG
grounding, a dissatisfied passenger, department routing, and the escalation
email actually leaving:

```bash
python e2e_check.py
```

### 5. Frontend

```bash
cd frontend
npm install
npm run dev                   # http://localhost:5173
```

## 📚 Knowledge Base (RAG)

The seed policy sheet (baggage, check-in, cancellations, special assistance, delays, escalation contacts) ships twice: [`docs/airline-rules.md`](docs/airline-rules.md) and the same content as [`docs/airline-rules-and-regulations.pdf`](docs/airline-rules-and-regulations.pdf). **The Markdown is the canonical ingest source** — its headings are what the structure-aware chunker splits on, while PDF extraction flattens them away.

To add knowledge:
1. Drop PDFs / Markdown / text files (`.pdf`, `.md`, `.txt`) into `docs/`.
2. Re-run `python backend/rag/ingest.py` — it re-chunks, re-embeds, and upserts into the ChromaDB collection. A document's previous chunks are deleted first, so renamed or removed sections do not linger.

**Near-duplicate handling.** Files are read structured-first (`.md` → `.txt` → `.pdf`), and a document whose vocabulary is ≥85% covered by what is already indexed is skipped as a restatement. That is what keeps the PDF twin out of the index — a content hash would not, because PDF extraction never reproduces the Markdown byte-for-byte. Pass `--allow-duplicates` to index everything anyway, or `--reset` to rebuild the collection from scratch.

## 🔌 API Endpoints (summary)

| Method | Endpoint         | Description                                        |
| ------ | ---------------- | -------------------------------------------------- |
| POST   | `/auth/register` | Create account (bcrypt-hashed password)            |
| POST   | `/auth/login`    | Returns JWT access token                           |
| GET    | `/auth/me`       | Verify the current token, return the account       |
| POST   | `/chat`          | RAG answer for a user query (auth required); accepts and returns `conversation_id` |
| GET    | `/chat/history`  | User's past queries from `query_logs`              |
| GET    | `/conversations` | User's conversation threads                        |
| GET    | `/conversations/{id}` | Every turn of one thread                      |
| POST   | `/escalate`      | Manually escalate a conversation to a department   |
| GET    | `/health`        | Liveness check + indexed chunk count               |

## 📨 Escalation Flow

1. After generation, the pipeline scores answer confidence (retrieval similarity + model self-check).
2. If the answer is low-confidence or the user marks it unhelpful, the query is classified into a department: **Baggage Services, Refunds Desk, Special Assistance, or General Support**.
3. An SMTP email is sent to that department containing the user's query, language, the full conversation transcript, and the retrieved policy context — enabling a human agent to pick up exactly where the AI left off.
4. The escalation is recorded in the `escalations` table with status tracking (`emailed`, or `pending_email` when SMTP is not configured) along with the exact email body that was composed. Escalating the same query twice is a no-op.

## ✅ Verified End to End

`backend/e2e_check.py` was run against the live Gemini API and a real Gmail SMTP
account. It exercises the exact path the escalation flow above describes:

| Step | Result |
| ---- | ------ |
| `GET /health` | `indexed_chunks: 9`, `knowledge_base_ready: true` |
| *"How much cabin baggage can I carry in economy class?"* | `kind: grounded`, confidence **0.7178** — answer quoted the 7 kg / 55×35×25 cm figures straight from `docs/airline-rules.md` |
| Follow-up in the same `conversation_id` | answered above the confidence threshold, so it did **not** auto-escalate |
| `POST /escalate` (`reason: user_marked_unhelpful`) | routed to **Baggage Services**; notice: *"Our Baggage Services team has received your query and will contact you within 24 hours."* |
| Escalation email | `status: emailed` — body carried the full transcript plus 5 retrieved policy excerpts with similarity scores |
| `python -m pytest tests -q` | **60 passed** |

Two things that run may be worth knowing if you fork this:

- **`gemini-2.5-flash` is closed to new API keys.** Google returns
  *"no longer available to new users… use models/gemini-3.6-flash"*. The default
  is `gemini-3.6-flash` for that reason.
- **The test suite must not touch the network.** `tests/conftest.py` blanks
  `SMTP_*` and redirects `CHROMA_DIR` to a tmp path; without that, a populated
  `.env` makes `pytest` authenticate to Gmail and send a real escalation on
  every run.

Note that the department contact addresses quoted *inside* `docs/airline-rules.md`
are illustrative (`baggage@skywings.example`), so the assistant will quote them
back to a passenger. The addresses escalation email is actually *sent* to are a
separate thing: they live in the `departments` table, seeded from
`config.DEPARTMENT_EMAILS` and overridable per-deployment with `BAGGAGE_EMAIL`
and friends in `.env`. `seed_departments()` reconciles a changed address on the
next start, so no manual DB edit is needed.
