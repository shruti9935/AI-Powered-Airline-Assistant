1. Elevator Pitch (30 seconds)

Say this in the interview "I built an AI customer-support assistant for airlines. Passengers ask questions in English, Hindi, Spanish, or French, and the system answers using Retrieval-Augmented Generation: it converts the question into a multilingual embedding, searches a ChromaDB vector store of airline policy and FAQ documents, and feeds the most relevant chunks to Gemini 2.5 Flash, which answers only from that retrieved context — so answers are grounded in real policy, not hallucinated. It's a full-stack app: React frontend, FastAPI backend, JWT auth with bcrypt, and MySQL for query logging. The part I'm most proud of is the human-in-the-loop escalation: when the bot can't confidently answer, it classifies the query into a department — Baggage, Refunds, Special Assistance — and emails that team the full conversation via SMTP, so no customer query is ever dropped."

2. Problem & Motivation

Airline support teams handle enormous volumes of repetitive questions — baggage limits, refund timelines, check-in deadlines — in many languages. A plain LLM chatbot fails here for three reasons:

  • Hallucination: an LLM will confidently invent a refund policy. In a domain with money and legal rules, a wrong answer is worse than no answer.
  • Stale knowledge: policies change (fees, timings). An LLM's training data can't be updated per airline.
  • No accountability: a pure bot has no path to a human when it fails.

3. Architecture & Request Lifecycle

What happens when a logged-in user asks "¿Cuánto equipaje puedo llevar?" (How much baggage can I carry?):

1React UI sends POST /chat with the query + JWT in the Authorization header.
▼
2FastAPI middleware verifies the JWT signature, identifies the user, rejects if expired/invalid (401).
▼
3Retriever embeds the Spanish query with gemini-embedding-001 → a ~768-dim vector in a language-agnostic semantic space.
▼
4ChromaDB runs cosine-similarity search → top-5 chunks. The English "Baggage Allowance" section matches even though the query is Spanish.
▼
5Generator assembles the prompt: system instructions + retrieved chunks + query + "answer in the user's language, only from context."
▼
6Gemini 2.5 Flash generates a grounded Spanish answer citing the baggage policy.
▼
7Logger writes query, language, retrieved chunk IDs, answer, and similarity scores to MySQL query_logs.
▼
8Confidence gate: if top similarity was too low or the model said it couldn't answer → department routing + SMTP escalation. Otherwise the answer streams back to React.

4. RAG Deep-Dive (the interview core)

4.1 What RAG is

Retrieval-Augmented Generation = search + LLM. Instead of asking the model to answer from its memory, you first retrieve the most relevant passages from your own documents, then ask the model to answer using only those passages. The LLM becomes a reading-comprehension engine over your data rather than an oracle.

4.2 Ingestion: hierarchical, structure-aware chunking

Naive chunking splits documents every N characters — which can cut a fee table in half or separate a rule from its exception. This project chunks along the document's own structure:

  1. Level 1 — sections: split on headings ("3. Cancellations & Refunds", "5. Special Assistance"). Each section is a semantic unit.
  2. Level 2 — passages: long sections are sub-split into paragraphs/table rows of ~300–500 tokens with ~50-token overlap so no rule is orphaned at a boundary.
  3. Metadata: every chunk stores doc_title, section, language — used for filtering and for citing sources in answers.

Worked example from the seed document airline-rules-and-regulations.pdf:

{
  "id": "swa-pol-2026#sec3#p1",
  "text": "3. Cancellations & Refunds — More than 72 hours: ₹1,500/sector;
           72–24 hours: ₹2,500; 24–4 hours: ₹3,500; under 4 hours: only
           taxes refunded. Refunds processed in 7 business days...",
  "metadata": { "doc_title": "SkyWings Rules & Regulations",
                "section": "Cancellations & Refunds",
                "language": "en" }
}
Key line "Structure-aware chunking matters because retrieval quality is the ceiling of RAG quality — if the right rule isn't in one retrievable piece, no LLM can answer correctly."

4.3 Embeddings: how a Hindi query finds English text

An embedding model maps text to a vector such that similar meaning → nearby vectors. gemini-embedding-001 is trained multilingually, so "सामान की सीमा क्या है?", "What is the baggage limit?", and "¿Cuál es el límite de equipaje?" all land close together in the same vector space. That's why the knowledge base can stay in English while queries arrive in four languages — cross-lingual retrieval with zero translation step.

4.4 ChromaDB: the vector store

  • A persistent local collection — embeddings survive restarts, no external service needed.
  • Query = embed the question, find top-k (k=5) nearest chunks by cosine similarity.
  • Metadata filtering: e.g. restrict retrieval to section = "Special Assistance" if the query classifier detects that intent.

4.5 Prompt assembly & grounding

SYSTEM: You are SkyWings Airlines' support assistant.
Answer ONLY using the context below. If the context does not
contain the answer, say you don't know and offer escalation.
Reply in the same language as the user's question.

CONTEXT:
[1] (Cancellations & Refunds) "More than 72 hours: ₹1,500..."
[2] (Flight Changes) "Date changes permitted up to 4 hours..."

USER: Mera flight kal hai, cancel karne par kitna refund milega?

The "answer only from context, otherwise say you don't know" instruction is the primary hallucination guard — and the "I don't know" path is exactly what triggers escalation.

4.6 Why Gemini 2.5 Flash?

  • Fast and cheap — a support chat needs low latency and low per-query cost; Flash is optimized for exactly this over the larger Pro model.
  • Strong multilingual generation — fluent Hindi/Spanish/French output.
  • Long context window — comfortably fits system prompt + 5 chunks + history.
  • One Google AI Studio API key covers both the LLM and the embedding model — simpler ops.

5. Multilingual Flow

  1. The React UI has a language selector; the backend also auto-detects language from the query text (Unicode script + model detection).
  2. Retrieval is cross-lingual (section 4.3) — no translation of the knowledge base needed.
  3. The generation prompt pins the reply language, so a French question about an English policy gets a French answer.
  4. The detected language is logged per query — useful analytics (e.g., "40% of refund queries are in Hindi → translate the refund FAQ page first").

6. Authentication & Security

Registration / Login

  • Passwords hashed with bcrypt (salted, slow by design) — never stored or logged in plain text.
  • Login returns a JWT signed with JWT_SECRET, containing user ID + expiry.

Per-request

  • Every /chat call carries Authorization: Bearer <token>.
  • FastAPI dependency verifies signature + expiry → stateless auth, no server-side session store.

Secret handling: the Gemini API key, DB credentials, JWT secret, and SMTP password live only in .env (git-ignored) and are read via environment variables — never hard-coded, never sent to the frontend.

If asked "why bcrypt?" "Fast hashes like SHA-256 can be brute-forced at billions of guesses per second. bcrypt is deliberately slow and salted, so even if the database leaks, cracking each password is expensive."

Why log retrieved_chunk_ids and top_similarity? Because when an answer is wrong, you must know whether retrieval failed (wrong chunks fetched) or generation failed (right chunks, bad answer) — they have completely different fixes.

8. Human-in-the-Loop Escalation

1Detect failure: top similarity below threshold (e.g. < 0.55), the model replied "I don't know," or the user clicks "This didn't help."
▼
2Route: classify the query to a department — keyword/embedding match against the departments table (e.g. "suitcase", "lost bag" → Baggage Services).
▼
3Email: smtplib over TLS (Gmail app password) sends the department the user's query, detected language, conversation transcript, and what the bot retrieved — the human agent starts with full context.
▼
4Track: an escalations row is created with status open; the user is told their query was forwarded and to expect a reply.
Key line "The design principle is that the bot's failure mode is graceful: it never dead-ends a customer. Every query either gets a grounded answer or a guaranteed human follow-up."

9. Likely Interview Questions — with Strong Answers

Q1. How do you prevent hallucination?
Three layers: (1) the prompt restricts the model to the retrieved context and instructs it to say "I don't know" otherwise; (2) low retrieval similarity blocks confident answers and triggers escalation instead; (3) answers can cite the source section, so they're verifiable. Grounding doesn't make hallucination impossible, but it turns "confidently wrong" into "honestly unsure — escalate."
Q2. What if retrieval returns nothing relevant?
That's a designed path, not an error. If the top similarity score is below the threshold, the system skips generation (or generates a polite "I couldn't find this in our policies"), routes the query to a department, and sends the SMTP escalation. Retrieval failure becomes a feature: it's the signal that a human is needed.
Q3. Why ChromaDB and not Pinecone / FAISS / pgvector?
For this scale (thousands of chunks, single node), ChromaDB gives persistence, metadata filtering, and a clean Python API with zero infrastructure — ideal for a self-hosted project. Pinecone is a managed service (cost, network dependency) that pays off at millions of vectors; FAISS is a raw index library without metadata/persistence conveniences; pgvector is great if you already run Postgres, but this stack uses MySQL. The honest answer: at my scale, any would work — I chose the lowest operational overhead.
Q4. How does a Hindi question match an English document?
The embedding model is multilingual: it was trained so that translations map to nearby vectors. "Baggage limit?" and "सामान की सीमा?" produce vectors with high cosine similarity, so the English policy chunk is retrieved directly — no translation step, no per-language document copies.
Q5. Chunk-size trade-offs?
Small chunks → precise retrieval but fragmented context (a fee slab without its exceptions). Large chunks → complete context but diluted embeddings (one vector averaging many topics) and wasted prompt tokens. I mitigated the trade-off structurally: chunk along headings so each chunk is one coherent policy topic (~300–500 tokens), with overlap so boundary sentences appear in both neighbors.
Q6. Why FastAPI over Flask/Django?
Native async — the backend spends most of its time waiting on Gemini API calls, and async lets one worker handle many concurrent chats. Plus Pydantic request validation, automatic OpenAPI docs, and dependency injection (used for JWT verification). Django is heavier than needed; Flask would work but adds async and validation as bolt-ons.
Q7. Why JWT instead of server-side sessions?
Stateless: the token itself proves identity via signature, so no session store lookup per request and easy horizontal scaling. Trade-off I can discuss: JWTs can't be revoked before expiry — mitigated with short expiry times and (if needed) a token blacklist for logout.
Q8. How would you scale this to production?
(1) Multiple Uvicorn workers behind a load balancer — stateless JWT auth makes this trivial. (2) Move ChromaDB to client-server mode or a managed vector DB as the corpus grows. (3) Cache frequent Q&A pairs (Redis) — support queries follow a Zipf distribution, so a small cache absorbs a large share of traffic. (4) A message queue for escalation emails so SMTP latency/failures never block chat responses. (5) Streaming responses via SSE for perceived latency.
Q9. How do you evaluate the system?
Two levels. Retrieval: a golden set of question → correct-section pairs, measuring hit-rate@k (is the right chunk in the top-k?). Generation: spot-check answers for faithfulness to the retrieved context, and track the escalation rate and user "didn't help" clicks as live quality signals. The query_logs table (chunk IDs + similarity per query) makes both measurable after the fact.
Q10. What was the hardest part?
Chunking real policy documents. Tables (fee slabs) and rule-exception pairs break under naive splitting, and retrieval quality — not the LLM — turned out to be the bottleneck. Moving from fixed-size to structure-aware hierarchical chunking with metadata was the single biggest quality improvement.
Q11. How is the department for escalation chosen?
Each department row carries keywords/descriptions; the query is matched against them (keyword match, upgradeable to embedding similarity against department descriptions — same technique as document retrieval, reused). Unmatched queries default to General Support, so routing can never fail hard.
Q12. What would you build next?
Hybrid retrieval (BM25 + dense vectors with reciprocal-rank fusion) — dense embeddings miss exact terms like flight codes and fee amounts that keyword search catches; a reranker over the top-20; an admin dashboard over query_logs; and response streaming. Each targets a measured weakness rather than being a feature for its own sake.
